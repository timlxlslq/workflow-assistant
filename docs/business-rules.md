# 已确认业务规则

## PP FlowHub 中央数据规则（已确认）

- PP FlowHub 是汇总层：AIHouse 提供设计事实，AIMES 提供工厂单，AICNC 提供生产报表，金蝶提供库存余额。
- 订单、工厂单、批次、材料、五金、出库单据编号和同步证据进入中央 SQLite；Traveler 不是生产文件，也不是业务事实源。
- 一个批次可对应多个工厂单；一个工厂单只能对应一个批次。发现同一工厂单的多个批次证据时不自动选择，建立异常提醒用户手工处理。
- 人工五金与 AICNC 五金保存在同一张五金表，用来源字段区分；AICNC 重同步只替换 AICNC 来源，人工五金不丢失。
- 订单详情按材料汇总显示；历史订单即使原始文件不在，也从数据库显示已保存的材料、五金、批次和出库单据。
- Traveler 不是订单中心业务流程的前置条件。订单和工厂单所需的材料、五金等数据以中央 SQLite 为准，正常查看、库存查询和出库不生成、不校验 Traveler。只有用户选中订单后，才允许按数据库数据按需生成 Traveler；生成后由用户自行另存到指定目录，或直接打印。

## 订单与工厂单模型

- App 的核心业务对象是“订单”，订单号下面可以存在一个或多个工厂单。
- AIMES 中出现工厂单，表示该订单已经“已拆单”；AIMES 的“销售单名称”是订单号的权威来源，工厂单号和工厂单名称是工厂单身份的权威来源。Server 文件夹和报表用于补充文件状态，不用于覆盖 AIMES 的订单归属。
- AIMES 最近页面之外的工厂单如果通过精确查询确认存在，精确查询返回的工厂单号、名称和销售单名称与最近页面数据具有同等身份权威性，必须一并写入本地数据库，不能只用于判断“未删除”。
- 本地 `factory_orders` 是工厂单身份的完整持久化索引；AIMES 每次读取的最近 50 条只是在线批量窗口，不能截断本地历史有效工厂单。Server 工厂单匹配时先按工厂单号复用本地数据库身份，只有数据库没有该工厂单号且无法从现有报表确认归属时，才允许调用 AIMES 精确查询。
- 订单中心展示普通订单下的工厂单时，优先采用 AIMES 销售单名匹配；已经在数据库中明确确认归属到该订单的 Server 报表或人工工厂单也必须展示，不能因为名称来源不是 AIMES 而从订单明细中过滤掉。
- 看板接受的 AIMES 订单号格式为 `PP` 加 4 位数字并可带数字后缀（如 `PP0035`、`PP0035-2`），或 `CS` 加 3 位数字（如 `CS004`）。PP 订单只显示 `PP0035` 及以后，阈值按主编号判断。AIMES 销售单名称不符合规则，或工厂单名称、销售单名称包含 `test`（不区分大小写）时，只在本次获取结果中提示并跳过，不写入订单、工厂单或 AIMES 映射缓存，不进入待处理中心；用户必须到 AIMES 修改原始销售单名称。只有格式有效的 AIMES 行才进入业务数据库。
- AIMES 获取成功后只保存有效的订单号、工厂单号、工厂单名称和现有批次映射；异常行作为本次操作警告显示。批次号仍按现有 Server 报表文件逻辑获取，不由本次 AIMES 改动覆盖。
- 一个房间不会被拆分到多个工厂单。房间名称无法可靠匹配工厂单时，必须提示用户手工分配，不允许猜测。
- 客户修改需求时，可以在同一订单号下新增一个工厂单。新增工厂单拥有不同的工厂单号和名称，是独立增加的生产任务；不建立“替代旧工厂单”关系，也不自动把原工厂单标记为作废。
- 新增工厂单产生的板材、封边条和五金均计入该订单的实际累计材料用量；历史工厂单的材料与出库记录继续保留。
- AIMES 精确核验确认工厂单已删除时，只在中央 SQLite 的 `factory_orders` 中保留删除状态、删除时间和最后核验时间用于追溯；该工厂单不显示、不计入订单状态、材料/五金、出库或待处理中心。仅凭最近 50 条当前页未出现不能标记删除，必须先做精确查询。

## 状态与证据

- `AIMES` 出现工厂单：工厂单“已拆单”。
- AIMES 获取固定读取当前页“50 条/页”，每次保存当前页工厂单快照；历史工厂单继续保留在本地数据库，最近页面之外的本地工厂单必须经过精确查询后才能标记为已删除。
- Server 出现订单号文件夹：订单已经进入优化/生产准备流程，但这不是 CNC 已经加工的证据。
- 已确认 material 中存在可映射到工厂单房间的有效材料明细：该工厂单“已优化”。订单下 AIMES 的全部工厂单均有对应证据时，订单“已优化”。
- 当前版本没有 CNC 加工记录来源，因此“真实生产”状态必须显示“未接入”或“待确认”，不能从文件夹、material 或 Traveler 推断为已生产。
- 库存状态来自最近一次库存系统查询，区分“未查询”“查询中”“库存充足”“库存不足”“查询失败”；查询失败后允许用户再次手工查询。
- 工厂单是否出库以库存系统出库记录为最终依据，不能以 App 曾经提交成功或本地文件状态代替库存系统记录。
- 订单和工厂单的业务状态必须持久化到本地 SQLite：AIMES 工厂单用于恢复“已拆单”，优化证据用于恢复“已优化”，库存同步记录用于恢复工厂单“已出库”；App 启动、订单索引读取和出库成功后都要重新核对这些来源，不能只依赖本次运行内存状态。
- 出库记录按订单号与工厂单名称/工厂单号匹配；若记录备注只有订单号，只有该订单当前唯一工厂单时才允许回填，避免把一次出库错误标记到多个拆分工厂单。
- 一张库存出库单可以覆盖多个工厂单；单据主表只保存一条单据事实，`outbound_document_factories` 保存该单据与每个准确工厂单号的关联。自动索引和对账必须按关联表逐个恢复工厂单状态，不能把多个工厂单号拼接后作为单一身份匹配。
- 订单下部分工厂单已有出库记录时，订单状态为“部分出货”；全部工厂单均有完整出库记录时，订单状态为“已出货”。
- “已出货”不是永久终态。订单已出货后，如果 AIMES 在同一订单号下新增未出库工厂单，订单立即回到“部分出货”；出货进度按最新工厂单集合重新计算，例如 `2/3 已出货`。
- 当前订单状态为“已出货”时，订单中心只允许计算成本；“查询库存”“设置出库范围”和“创建出库”均不可用。订单因新增未出库工厂单回到“部分出货”后，按当前工厂单事实恢复相应操作。
- 单个工厂单出库时同时处理其板材/封边条和五金；确实没有五金的工厂单显示“无五金/不适用”，不能显示“未出库”。
- 板材和封边条允许按工厂单分批出库，订单级出库记录累计保存，并在备注中记录本次覆盖的工厂单名称；五金继续按具体工厂单出库。

## 订单发现

- `Optimized Orders` 是自有订单，`CUT TO SIZE` 是来料加工订单。
- 截止日期由用户调整，两个来源共用一个日期；日期前文件夹不处理。
- 列表显示所有文件夹，已生成 Traveler 和已忽略项灰显。
- 未生成 Traveler 的订单不跟踪源文件变化。已生成 Traveler 后，文件修改时间只作为“需要重新读取”的触发条件；是否需要更新 Traveler 最终以材料、工厂单身份和五金等业务内容指纹为准。
- 异常名称文件夹提醒人工处理；用户忽略后不重复提醒。
- PC 批次日期从批次号解析，不读取 AIMES。

## Traveler

- 模板固定为 `resources/templates/Work Order Traveler.xlsx`。
- 前三个工作表唯一合法名称及顺序为 `WorkOrderTraveler`、`Usage List`、`Picking List`。
- 新 Traveler 不覆盖。更新前立即备份，在临时路径完成并重新打开验证后原子替换。
- `Usage List` 明细从第 3 行开始。同一房间多颜色占多行，房间名后续行留空，不纵向合并。
- 明细超过 11 行时在 `Total Qty:` 之前插行，同步延长汇总公式。
- Plywood 只在 `Total Qty:` 汇总；Panel 和封边在 `Color Table` 按颜色汇总。
- 人工 material 仍填写房间明细，由模板公式形成 `Total Qty:` 和 `Color Table`。生成 Traveler 时，Plywood 以 material 的 `Total Qty:` 为订单权威值，Panel 和封边条以 `Color Table` 为订单权威值；房间明细用于保留原始依据和映射工厂单，不得用重新计算的结果覆盖人工确认汇总。
- 读取 material 时，Panel/封边明细行只要有数量就必须填写 `Color`；同时校验 `Total Qty:` 中的 Panel/封边合计与 `Color Table` 各颜色合计一致。发现颜色为空或合计不一致时，阻止本次材料事实写入，进入待处理中心并要求用户手工修正后重新扫描；数量为空的模板空行不触发此校验。
- 订单缺少 material 文件时先询问用户；确认后可从 Report 的板材清单自动生成。自动文件必须沿用人工 material 模板的表格格式、字体、合并单元格、行列尺寸和备注，并使用兼容的 `SUM` / `SUMIF` 公式汇总 Plywood、Panel 与封边条。报表结构过于复杂、超过模板容量、规格无法安全归类或文件无法读取时，不生成半成品，并提示用户手动生成。
- App 自动生成 material 或在校验时执行明确的 Color Table 修正后，只将实际写入的 material 文件及其订单根目录登记为本次 Server 基线；同目录其他报表不随之被忽略。之后 material 被外部修改时仍必须重新提示 Server 变化。
- `Picking List` 中每个工厂单分开显示五金，不显示订单级五金合计。
- `Picking List` 没有业务内容时（包括无工厂单和五金的 `CUT TO SIZE`），保留原模板全部行列、合并单元格、行高、列宽和样式；只清除工厂单和明细业务数据，不新增提示行。
- 人工五金必须归属某个工厂单，且仅写入 `Hardware Accessory五金功能件`。
- 用户设置为忽略的五金按名称、商品编号或已确认显示别名全局生效：不写入中央 SQLite，不生成 Traveler，也不进入库存出库；设置忽略时清理已有同项硬件事实，恢复忽略后只对后续重新同步的数据生效。
- 订单材料、封边和五金写入中央 SQLite 前必须通过当前商品资料表的启用 SKU、有效人工映射或全局忽略；未完成项目阻止本次事实替换并进入待处理问题，不能先删除旧事实再留下半成品。AICNC 的 `WJ-*` 等来源编码只保留为来源/显示追溯信息，不视为库存 SKU。
- 同一工厂单在多个 Fittingslist 中出现时，数据库入库和 Traveler 预览统一按文件修改时间选择最新文件；内容一致的重复文件自动去重，最新时间相同但内容不同则阻止该工厂单写入并要求人工检查。
- 当前已确认映射包括：`Hinge`/`TestFullHinge`→`M1001`、`Adjustable shelf holder`→`M1013`、`Cloth rod bracket - Fitting`→`M0179`、`Edge banding--Penelope FA44`→`M1043`、`19.1mm--Penelope FA44`→`M1042`、`8mm--Woodline 3`→`M1147`、`19.1mm--Walnut`→`M0159`、`Edge banding--Walnut`→`M0160`。忽略规则只读取用户维护的全局忽略列表，不内置任何特定商品的特殊忽略。
- 设置页分别提供“材料映射”和“五金全局忽略列表”的查看入口；点击后在各自专用管理界面中查看、新增、修改和删除。
- 材料映射和五金忽略规则统一保存在中央 `workflow.sqlite3` 的 `inventory_resolution_rules` 表中；`source_name` 保留用户输入的显示名称，`normalized_name` 只用于匹配。运行时不再读取或写入映射/忽略 JSON 文件，旧文件迁移成功后仅归档用于回滚。
- 订单详情、成本计算、库存预检和数据库出库均以中央 SQLite 订单事实为业务来源；Traveler 是按需生成的打印/导出文件，不是这些业务流程的必经前置条件。
- 来料加工订单（`order_type=cutToSize`）允许客户提供板材和封边：源文件读取的材料事实仍写入中央 SQLite，但用户可在订单中心单独确认“客户提供，不出库”；该选项不适用于自有订单，也不适用于五金。
- 客户材料且没有有效五金时，订单中心的“创建出库”确认只写入数据库并将工厂单显示为“已出库”；数据库另存 `outbound_mode=customer_supplied` 以区分库存系统真实出库，不能伪造库存单号。若有本公司材料或有效五金，则仍进入库存系统出库。
- 余料生产/其他无需出库必须由用户明确确认并记录原因；“数据库没有材料”不构成余料生产判断。出库范围变化后，订单中心只做数据预检和真实确认执行。
- 添加人工五金时按 SKU 读取本地商品资料，不查询实时库存；数量必须是正整数。
- 同一工厂单中 SKU 和规格相同的人工五金合并数量，不重复新增行。
- 更新五金只与最近批次比较，不累加历史批次。
- 更新 Traveler 不自动出库。数量已出库且发生变化时，另行提醒用户处理原出库单。
- 判断 Traveler 是否需要更新时比较业务内容，不比较文件修改时间。仅修改时间变化但材料、工厂单身份和五金数量均未变化时，显示“内容一致，无需更新”。

## 混单和临时单

- 一个 PC 批次可同时生产不同订单的房间；同一订单可对应多个 PC 批次。
- 能确定分单时自动分配板材和封边；不能确定时显示面积占比、自动取整建议并要求确认。
- 确认后把分配结果写入各订单 Traveler。
- Server 扫描时先按文件夹名称判断订单类型：标准 `PP####`、`PP####-#` 为自有订单，标准 `CS###` 为来料加工订单，名称中包含两个及以上完整订单号的非标准文件夹为混单，其他可处理的非标准文件夹为临时订单。
- 文件夹名称只是扫描分类依据；文件夹时间变化本身不代表报表内容发生变化。只有文件新增、删除、修改，或报表/业务内容指纹发生变化时，才应形成需要处理的变化。
- 临时订单不使用销售单格式异常的 AIMES 行进行自动匹配；没有有效 AIMES 映射时，按临时订单规则处理，不猜测订单归属。
- 没有 AIMES 匹配的临时订单，其用户可见身份统一使用文件夹名称：Traveler 的 `WorkOrderTraveler` 订单号、`Usage List` 订单号、`Picking List` 工厂单名称和库存出库备注均使用文件夹名称；内部工厂单号可以为空。Traveler 中标记为“临时订单”。
- 没有唯一工厂单标识不妨碍临时订单出库：板材和五金可以一起出库，库存备注使用文件夹名称，不能要求用户补造 `F` 加数字的工厂单号。
- 临时订单生成或更新 Traveler 时，用户可以选择是否包含五金。关闭后不读取、不写入五金，即使文件夹中存在 Fittingslist；库存出库完全按照最终 Traveler 内容执行。
- 临时订单缺少可识别报表、格式不符合、材料映射失败或库存出库失败时，保留在统一待处理中心，不推进该文件夹的处理基线，并显示具体原因和相关文件。
- 临时订单必须有稳定的内部身份，不能只依赖文件夹名。内部身份至少结合规范化路径、文件系统 inode 和文件夹创建时间；数据库保存文件夹、内容指纹、处理状态、出库状态、出库单号和时间。
- 同一临时文件夹内容未变化且数据库已记录“已出库”时，再次扫描、手工处理或待处理中心处理不得重复出库；文件内容变化后才允许重新处理。
- Traveler 成功生成后保存“Traveler 生成指纹”、生成时是否包含五金、生成状态和生成时间。临时订单出库失败后重试时，如果报表内容指纹、五金选项、Traveler 状态和 Traveler 文件均未变化，直接复用现有 Traveler 出库；否则重新校验并生成或更新 Traveler。

## Server 扫描与统一待处理中心

- 顶部只保留一个待处理警示图标和入口。Server 文件夹变化、订单处理失败、订单归属问题和报表检查进入待处理中心；销售单格式异常只作为 AIMES 本次获取警告显示，不进入待处理中心。
- 待处理中心以文件夹或问题为主记录，不以单个文件作为主记录。同一个文件夹只能出现一条主记录；文件变化、解析失败、格式问题、订单归属不明、材料映射失败和出库失败都挂在该文件夹记录下。
- Server 扫描到的文件夹显示为一条记录，展开后显示新增、修改、删除和缺少报表等明细。新增文件显示创建时间，修改文件显示修改时间，删除文件显示记录时间；显示格式使用 `YYYY-MM-DD HH:mm:ss`，不显示日期和时间之间的 `T`。
- 用户可勾选需要自动处理的文件夹，点击“自动处理”后只处理勾选项；未勾选项继续保留。需人工确认的问题不能被自动处理按钮绕过。
- “稍后处理”只关闭当前界面，不解决问题、不推进处理基线；之后扫描仍应继续提醒。
- 待处理中心中的 Server、订单问题和 AIMES 问题可以合并展示，但必须保留来源、问题类型、后台状态和可执行的处理方式。
- 混单文件夹缺少可识别报表时，提示用户检查，并允许选择“忽略此文件夹（观察一个月）”。观察期内文件夹元数据或可识别报表状态发生变化，重新提醒；一个月内没有变化则永久忽略。
- 启动时可以先显示本地缓存，但后台 Server/AIMES 检查期间不应自动弹出锁定待处理中心。后台扫描完成后才依据最新结果决定是否弹出；用户始终可以关闭待处理中心回到主界面。
- 自动处理失败后，失败原因必须进入主界面操作记录和统一待处理中心；失败不应因为关闭弹窗或回到主界面而丢失，也不应再次强制打开待处理中心阻塞用户。
- 操作记录和悬停详情只显示当前操作相关的订单、文件和业务原因。批量读取 Server 时按文件夹归纳下属 material、板材清单和五金清单数量，不逐条堆叠完整绝对路径；Excel 无法读取时必须显示具体失败文件名，不显示局部变量错误、堆栈或其他无关操作内容。
- 当前待实现：后台“正在自动处理 Server 变化、解析报表并准备出库”等状态提示应显示当前处理身份：标准订单显示订单号，混单显示涉及的订单号，没有标准订单号的临时订单显示文件夹名称。

## 库存

- 库存查询默认只检查板材和封边，可选临时或持久加入五金；不使用查询缓存。
- 查询时仓库留空。结果表无数据即库存为 0，不再切换其他显示选项。
- 不比对跨系统单位文字。
- 板材和封边按订单号出库；五金按工厂单名称出库，可一次选择一个或多个工厂单。
- 封边原数量单位为 m；material 解析按 `Total Qty:` 或 `Color Table` 单元格的 Excel 显示值读取，整数格式使用 `ROUND_HALF_UP`，本地业务事实和库存出库均使用该显示整数。其他材料本就是整数。
- 库存不足仍允许出库，但必须明确警告。
- Traveler 数量减少且已出库时，经确认后修改原出库单。
- 标准工厂单出库前必须以订单索引 SQLite 的工厂单号和 `outbound_status` 为第一道硬门槛：查询到该工厂单已出库时，订单中心不得允许勾选或点击出库按钮。
- 若 Server 上与该工厂单关联的报表文件发生实际内容变化，必须先比较内容指纹并提示用户“可更新出库信息”；只有用户明确确认后，才允许进入原出库单更新流程。更新成功后必须同时更新原出库单、库存同步记录、订单索引 SQLite 中的工厂单出库信息，以及 Server 文件内容指纹/处理基线；不得直接新建重复出库单。仅修改路径、修改时间或文件大小而内容未变化，不构成允许更新的依据。
- 临时订单的板材和五金出库备注使用临时文件夹名称；不能用空备注，也不能依赖不存在的工厂单号识别出库。
- 出库成功后同时写入库存同步记录和临时订单台账；台账用于跨 Server 自动处理、手工选择文件夹和待处理中心重试入口识别同一个临时订单，防止重复出库。
- 出库失败不等于已出库，不得写入成功出库状态；重试是否重新生成 Traveler 由 Traveler 生成指纹和五金选项比较决定。
- 库存网页操作优先复用 App 打开的库存专用 Chrome 中已登录的 `jdy.com` 及其子域名工作台页面（包括按租户或区域跳转的地址，如 `vip2-hz.jdy.com/default-new.jsp`）；登录入口使用 `https://www.jdy.com/login/`。复用成功时不重新登录、不读取库存系统钥匙串密码。没有已登录页面时才使用原有 Playwright 登录流程。
- 库存专用 Chrome 使用独立用户资料和本地 CDP 端口。普通用户直接启动且未开放 CDP 的 Chrome 不由 App 强行接管；App 完成操作后只断开调试连接，不关闭用户的专用 Chrome。
- 更新商品资料成功后显示本次资料摘要：最终总数、新增数量、资料内容更新数量和删除数量。
- 用户正常退出 App 时，如果本次 App 启动了库存专用 Chrome，则关闭该专用 Chrome；不会关闭普通 Chrome。强制退出、崩溃或断电不保证执行退出清理。

## 操作边界

- 所有命令可文字或语音输入；写文件和写库存前必须本地确认，确认也可文字或语音完成。
- 任务串行执行并显示队列。未处于真实写入阶段时可取消。
- 订单中心按数据库数据工作的新流程不依赖 Server 上的 material 或 Traveler 文件；Server 不可用时仍可查看已缓存的订单/工厂单材料详情。库存系统不可用时仍禁用真正的库存查询/出库执行，但不影响本地数据库详情查看。
- 服务器路径变化或模板异常时直接提醒用户处理。
- 库存系统出现验证码、滑块、安全验证或登录失效时，后台自动化不得绕过验证；应暂停并提示用户在库存专用 Chrome 中完成验证后重试。

## 订单看板与页面操作

- 8 张订单统计卡片显示在“助手”页面顶部；订单中心继续作为独立页面，保留搜索、状态筛选、AIMES/Server 操作、操作记录、订单列表和工厂单详情。移动统计卡片不得改变顶部“订单中心”导航或默认页面。
- 订单表格使用“状态”作为列名，不再称为“阶段”。状态选项为已设计、已拆单待优化、部分优化、已优化、部分出货、已出货、待确认和数据异常；其中已设计表示订单设计已经建立但尚无 AIMES 工厂单。当前看板只显示 AIMES 已发现工厂单的订单，因此该状态暂时不会实际显示。
- “数据异常”必须保存并展示面向业务用户的原因；鼠标悬停在状态上时显示发生了什么、影响什么以及建议的下一步操作，不显示异常代码、状态码、堆栈或其他底层实现细节。其他页面的错误提示遵循相同原则。
- App 启动时先从本地 SQLite 订单数据库显示上次缓存，不等待 AIMES 或 Server。随后检查当天是否已有成功的 AIMES 获取记录：已有则略过；没有则后台获取，只有业务数据发生变化时才刷新看板，失败时明确提醒并保留缓存。
- 每次启动均可在后台轻量扫描 Server，只比较订单文件夹和目标报表的路径、修改时间及大小，不在扫描阶段解析 Excel 或改变订单状态。名称可解析出两个及以上完整订单号的非标准目录（例如 `CS003 PP0047`）按混单文件夹处理，不按临时订单处理。发现新增、修改或删除时弹出待处理清单；用户点击“自动处理”后才解析报表、更新数据库和刷新看板，选择“稍后处理”则后续扫描继续提醒。
- [历史流程，待迁移] 真正的临时文件夹在用户点击“自动处理”后校验文件格式并生成或更新 Traveler。该规则不作为订单中心新流程的前置条件；新流程应直接把解析后的业务数据保存到 SQLite，再由用户在选中订单后按需导出 Traveler。
- Server 待处理弹窗按来源文件夹分组，不按单个文件决定处理范围；每个文件夹下显示新增、修改或删除的文件明细。用户必须先勾选文件夹，点击“自动处理”只处理勾选的文件夹，未勾选项继续保留在待处理清单。
- 看板手工操作分为“获取 AIMES”和“扫描 Server”两个独立按钮；获取 AIMES 不扫描 Server，扫描 Server 不登录 AIMES，也不自动处理变化。无论 App 启动后的自动 Server 检查还是手工点击“扫描 Server”，都必须同时检查 `Optimized Orders`（自有订单）和同级 `CUT TO SIZE`（来料加工）两个目录；订单号以 `PP`/`CS` 路由到对应目录。扫描完成后允许后台刷新本地订单索引，以便看板反映已存在的优化产物；即使发现待处理变化，也必须保留待处理清单，仍不得自动处理报表、生成 Traveler 或出库。
- Server 订单索引刷新采用增量策略：未变化的板材清单和 `Fittingslist` 复用本地 SQLite 已保存的解析身份和状态；只有新增、修改或删除的报表重新解析并校验受影响订单。新出现的 `Optimize file.xml` 或 `nesting_result.xml` 只做轻量产物检查，不重复打开全部 Excel。首次建立索引、显式处理选定文件夹或 `sync-index --full-refresh` 仍执行完整校验；该优化不改变订单归属、优化状态证据或待处理变化的业务规则。
- 自动扫描 Server 时，标准订单文件夹只有在存在未出库、部分出库、状态未知或 AIMES 新增的工厂单时才进入扫描范围；全部已出库的标准订单文件夹完全跳过，不读取其内部文件。用户手工选择文件夹处理时不受该自动候选过滤影响。
- 订单行默认显示订单级摘要；点击展开后在原位置显示该订单下的工厂单状态，避免用户为查看每个工厂单反复切换页面。
- 看板订单按 AIMES 拆单时间倒序排列；一个订单有多个工厂单时，以其中最新的拆单时间作为该订单的排序时间。工厂单明细也按拆单时间倒序排列。
- 点击订单号或“查看详情”展开订单时，直接显示工厂单表格；不再显示摘要卡、详情标题或页签切换条。材料、Traveler、库存查询和出库通过顶部上下文操作进入既有流程。
- 订单中心快捷操作进入现有生产文件或出库流程时，应自动带入并选中当前订单，复用既有预览、库存校验、确认和操作记录逻辑。
- 工厂单明细只显示工厂单身份、拆单、优化、出库和 Panel 颜色；Panel 数量属于订单级总量，不在工厂单行中虚构拆分。
- 展开订单后的工厂单表格整体从左侧开始排列；每列标题和内容只在自己的列宽内居中。订单级 Panel 颜色摘要单行显示并使用较大字体。
- 订单中心新流程（已实现）：订单/工厂单选择、材料详情、库存查询和出库预览均直接使用 SQLite 中已保存的数据，不得再以 Traveler 文件存在、material 文件存在、Server 可访问或 Traveler 校验结果作为按钮门禁。订单选中后提供“生成 Traveler”操作，按数据库数据生成文件，并提供用户选择目录另存和打印；该操作是导出动作，不回写或替代数据库事实，也不参与正常订单流程。订单中心出库不生成、不读取、不校验 Traveler。
- 选择工厂单后查询库存时，弹出带工厂单上下文的库存比对窗口；在现有数据源仍提供订单级库存结果的阶段，数量按订单级材料需求展示并明确标注。
- 从订单中心选择一个或多个工厂单创建出库时，弹出带订单和工厂单上下文的出库预览窗口，不显示左侧 Traveler 文件列表；预览只包含数据库中的订单级材料与所选工厂单内容，并继续执行商品映射等原有出库前校验。
- 数据库数量为 0 的材料不作为出库预览行显示，也不写入库存系统；该信息仅保留在机器可读诊断结果中。独立 Traveler 入口按 Traveler 数量执行同样规则。
- 出库当前操作、成功、失败、警告和历史过程统一进入内容区下方的消息记录框；顶部导航区域不显示独立或重复状态消息。消息记录框固定高度，只有记录内容区域滚动，底部操作按钮保持固定。
- 看板当前状态和历史数据变化统一放入一个可滚动消息记录框，不在搜索/筛选区下方另设状态文字；记录框不显示“看板操作记录”或“最近 N 条”标题，一次固定显示 3 条紧凑记录，全部消息显示更新时间，并按时间从旧到新排列、自动滚动到最新一条。记录框上方显示当前正在进行的操作；空闲时显示最近一次成功、警告或失败结果。AIMES 与 Server 的待处理、已忽略和已确认入口保留在对应消息行中。
- AIMES 耗时显示使用后端返回的单一总耗时；阶段列表只包含互不重叠的实际阶段，不得把“总计用时”再次作为阶段显示。在线精确核验、数据库写入以及后端准备/收尾若属于总耗时范围，必须分别计入阶段或明确显示为补齐阶段。
- 待办继续作为独立功能，不根据订单业务状态自动创建或改变待办。
- Dashboard 使用现有 App 默认窗口大小和现有最小尺寸约束，不修改默认窗口尺寸；窄窗口通过自适应列、截断、展开和滚动避免组件遮挡。

## 版本范围

- 当前版本只设计和实现订单中心、订单/工厂单状态汇总及现有生产文件、库存、出库流程的入口整合。
- WeCom `Order Management` 的自动同步暂不实现；当前手工建立的智能表格不能作为本版本的官方 API 数据源。
- CNC/机器加工记录和真实生产状态接入暂不实现，留待下一版本调查数据源后设计。
- 后续实现订单看板时优先复用现有 `AppPalette`、`AppLayout`、`AppSurfaceCard`、`AppStatusBadge`、`OperationLogCard`、订单预览和库存比较模型；只有现有组件无法表达已确认交互时才新增组件。

## 业务规则文档维护约定

- `docs/business-rules.md` 是跨订单、Server、AIMES、Traveler、库存和待处理中心的业务规则总文档；`docs/inventory-outbound-rules.md` 是库存查询与出库的专项契约。
- 后续任何对话中确认、修改或废止业务逻辑时，必须在同一次代码修改中同步更新对应 Markdown 文档；如果只讨论、暂不修改代码，则先记录为“待实现”或“待确认”，不得写成已完成规则。
- 每次业务规则修改同时在 `docs/project-handoff-log.md` 增加一条记录，说明用户要求、规则变化、影响范围、验证状态和未验证的生产条件。
- 文档中的规则必须区分“已确认并已实现”“已确认但待实现”“待用户确认”和“未验证生产条件”，不得用单元测试或构建成功代替真实 Server/库存系统验收。
