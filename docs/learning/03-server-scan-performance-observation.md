# Server 扫描性能观测

## 本次做法

Server 轻量扫描继续使用现有的全量目录遍历，并按“路径 + 相关报表文件的修改时间标记 + 文件大小”与已处理基线比较。订单文件夹本身只用于发现、归属、分组以及新增/删除判断；文件夹 mtime 单独变化不再视为业务变化。修改时间标记使用毫秒精度，避免把纳秒值写入 SQLite REAL 列时发生浮点精度丢失。扫描结果额外记录：

- 扫描耗时（秒，保留两位小数）
- 扫描到的订单文件夹数量
- 检查的相关 Excel 文件数量
- 快速检查的相关 Excel 文件数量
- 复用的订单文件夹数量
- 深度扫描的订单文件夹数量
- 新增、修改、删除数量

这些数据通过 scan-server 返回的 server.scan_stats 提供，同时转换成中文 operation_trace[server]，在订单中心 Server 消息的悬停详情中显示。索引读取详情按文件夹汇总下属 material、板材清单和五金清单数量，只展示少量文件夹示例；完整绝对路径仍保留在索引和具体错误记录中，便于人工定位。

当前扫描器仍会递归枚举每个自动候选订单文件夹，因此现阶段“复用文件夹”为 0，“深度扫描文件夹”等于本次扫描范围内的订单文件夹数量。“快速检查文件”表示只读取相关 Excel 的路径、修改时间和大小，不打开工作簿内容。保留这组三项稳定统计，是为了让后续文件夹快照复用上线后能够直接比较优化前后的真实效果，而不改变界面口径。

## 索引更新的增量策略

`scan-server` 仍然只做目录、路径以及相关报表文件修改时间和大小的轻量比较，不打开 Excel。随后启动的 `sync-index` 已改为增量更新：

- 未变化的板材清单和 Fittingslist 复用 SQLite 中上次解析出的工厂单身份、订单归属和五金状态；
- 新增、修改或删除报表只重新校验受影响的订单；
- 新生成的 `Optimize file.xml` / `nesting_result.xml` 只做轻量文件存在性检查，不因此重新打开全部 Excel；
- 首次建立索引、显式选定 Server 文件夹或传入 `--full-refresh` 时仍可完整校验。

因此，扫描到 0 个文件变化时，不再重复打开当前 Server 下全部业务 Excel。当前实机 App 记录的 64 秒同步中，约 33 秒用于 112 个文件的登记与解析窗口，约 31 秒用于 13 个订单的重复校验；优化后第二次无变化刷新应主要保留 SQLite 和产物元数据检查。

## 为什么先观测，不提前复杂化

目录快照或增量事件跟踪可能减少 Server 网络盘上的枚举次数，但会引入目录 mtime 不代表子文件内容变化、网络盘事件能力不一致、快照失效和恢复等正确性风险。当前优先记录真实扫描耗时和扫描规模，先确认瓶颈是否实际存在，再依据数据决定是否需要更复杂的算法。

本次未改变 Server 扫描仍为只读的边界，也未改变订单归属和优化状态的业务含义；仅把已确认的文件元数据与索引缓存用于安全复用。真实 SMB 挂载上的耗时改善仍需安装版现场复测。
