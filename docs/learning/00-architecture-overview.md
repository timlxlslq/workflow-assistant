# 学习：为什么是 App + Agent + Skills

Skill 是某个业务领域的标准作业说明，Agent 是根据用户目标选择下一步的协调者，App 是提供状态、预览、语音和审批的产品。

本项目不把其中任何一个当成“全能层”：

- Skill 不实现 Excel 算法，只说明何时调哪个工具。
- Agent 不获得无限制文件或浏览器权限。
- Gateway 不是 MCP 服务；它是应用内部的类型化安全边界。
- CLI/Python 不理解模糊语言，只执行可重复的业务函数。

这种分层同时带来两个好处：常用操作不消耗 Token，真实写入又不会因为 Agent 的语言推理而变得不可预测。

## 第一次 Agent 接入学到了什么

本阶段没有让 Agent 直接调用 Excel 工具，而是先让它输出严格的数据结构：`action`、`order_id` 和一句解释。原因是它当前只需要理解模糊表达；结构化输出比“调用一个只负责返回动作的假工具”少一次模型循环，也更省 Token。

模型返回后仍要经过本地校验：订单号必须符合 PP/CS 格式，写入动作是否需要审批由 Gateway 决定，不能相信模型自己声明权限。成功识别的整句话会以精确匹配方式保存到 SQLite；以后同一句话零 Token 执行，但相似句不会被擅自泛化。

当前真实 API 冒烟测试已通过。用虚构订单号输入时，Agent 正确返回 `preview_order`，使用 261 个输入 Token 和 34 个输出 Token。完整链路测试中，一条模糊的订单列表语句首次由 Agent 识别，共使用 287 Token；第二次输入同一语句时命中 `learned_local`，使用 0 Token。这证明 API 计费、结构化路由、Gateway、SQLite 学习和用量统计已经连通。

## 依赖声明为什么也是架构的一部分

第一次在 Agent 专用虚拟环境运行完整测试时，发现 `pyproject.toml` 漏掉了项目早已使用的 `openpyxl`。App 打包时会复制 `vendor/openpyxl`，所以这个问题容易被本机环境掩盖；但干净虚拟环境能立即暴露它。现在项目明确声明与现有 vendor 一致的 `openpyxl 3.1.5`，使下一个工具或开发者能从项目本身知道完整运行依赖。

## 为什么任务要串行

当前使用者只有一人，也没有并行生产任务的需求，因此一个任务完成后再运行下一个最容易理解。App 可以继续接收输入并把任务显示为“排队中”。取消不是简单地停止按钮：排队、读取和等待确认都没有真实副作用，可以取消；一旦进入 Traveler 文件写入或库存写入，取消入口立即关闭，避免留下只完成一半的数据。

## 人工五金功能如何经过各层

用户可以说或输入一条标准命令，例如“给 PP1234-2-LAUNDRY 添加人工五金 M0144 数量 2”。本地解析器只提取订单号、工厂单名称、SKU、数量和备注，因此这条常用路径不消耗 Token。Gateway 从本地商品资料取得商品名和规格，显示完整预览并等待确认。确认后，Python 只写入对应工厂单的 `Hardware Accessory五金功能件` 区域，先备份，在临时文件中保存并重新打开校验，最后原子替换原 Traveler。

模糊说法的真实测试暴露了一个重要边界：Agent 可能把 `PP9999-KITCHEN` 拆成 `order_id=PP9999` 和 `factory_name=KITCHEN`。本地程序不盲目信任这个结果；只有订单号和房间名都确实出现在用户原句中时，才重组为完整工厂单名称。修正后，模糊命令首次使用 573 Token 并停在审批；确认时从 SQLite 读取全部类型化参数，使用 0 Token。

## 库存查询为什么不需要 Agent

“从 Traveler 取得 SKU → 打开商品库存余额表 → 查询数量 → 计算短缺”是一条确定性流程，不需要模型判断。App 在 Traveler 商品映射预检通过后直接调用 Python CLI；Python 只把板材和封边汇总成查询契约，Playwright 逐个查询，最后由 Python 计算 `max(需求 - 库存, 0)`。整个过程使用 0 Agent Token。

查询与出库共用同一套 Traveler 解析和商品映射，但权限不同：库存查询是只读操作，不需要审批；出库会写入真实系统，必须进入本地审批状态机。把两者放在同一个 inventory-management 领域中复用规则，同时保留两个不同工具动作，正是“Skill 不过细拆、代码按职责拆”的具体例子。

## 为什么界面采用左侧导航

最初版本用顶部标签页承载助手、生产文件、出库、待办和设置。功能增加后，标签宽度、页面标题和操作按钮挤在同一条水平线上，窗口稍窄就会显得杂乱。现在改成固定的左侧领域导航，右侧每一页统一使用“页头 → 状态/主要操作 → 内容卡片”的结构。这符合 macOS 桌面工具常见的信息层级，也让以后增加页面时不需要继续压缩顶部空间。

界面尺寸集中在 `AppLayout`：页面边距 18、主要控件高度 32、导航宽度 164、卡片圆角 10。颜色只使用系统背景、系统强调色和成功/警告/失败三种状态色；业务按钮不再各自决定任意大小。这里的“设计系统”只是少量共享常量和 View 修饰器，没有引入额外 UI 框架或配置文件。

本次还暴露了一个交互契约问题：“保存全部配置”原来只保存普通设置，并不会保存密码。按钮名称与真实行为不一致会让用户误以为配置已经完成。现在只要密码输入框非空，该按钮就同时保存用户名和 macOS 钥匙串密码；密码仍不会写入 JSON、SQLite 或日志。

App 与 CLI 的进程身份不同，直接调用 `/usr/bin/security` 会出现 App 已保存、CLI 却找不到的情况。现在项目只保留一条存取路径：SwiftUI 用 Security Framework 写入，本地 `keychain-read` 辅助程序用同一 Framework 读取，Python 只接收辅助程序的返回值。这样密码既不进入命令行参数，也不出现在配置文件和日志中。

真实库存查询还验证了两个页面自动化原则：复选框必须触发真实点击，不能只修改 DOM 外观；工作台菜单和报表正文位于不同 iframe，必须分别定位。M0144 的实测结果表为空，程序按业务约定返回库存 0；全过程为本地确定性工作流，Agent Token 为 0。

## CS004 为什么必须保留空白 Picking List 模板

`CUT TO SIZE` 订单没有工厂单和五金。原程序先删除 `Picking List` 模板内容，再按工厂单循环创建区块；CS004 的循环次数为 0，所以工作表最后只剩标题。这是典型的“空集合边界条件”：正常 PP 订单测试都会进入循环，因此无法暴露。

新的业务要求说明，空状态不应自创提示文字，而应是“原模板的完整空白状态”。因此现在的 materials-only 分支不再删行、删列、解除合并或重建样式，只清空工厂单和数字行中的业务单元格。库存解析器同步允许空白的“Name/工厂单名称”模板行；如果后续真的出现五金数据但仍没有工厂单，仍然报错。

回归测试不再只检查几个文字或单个合并区域，而是把生成结果与同样经过一次 openpyxl 存档的未修改模板比较：行列数、全部合并区域、行高、列宽和单元格样式必须一致。这种“结构快照”比检查一条提示语更能保护 Excel 模板契约。

## 库存页按钮为什么使用自适应网格

库存页同时有资料刷新、材料处理、库存查询、模拟填写和真实写入等多组操作。固定 `HStack` 在宽窗口里看起来正常，但窗口缩小后只会压缩文字和间距，不会自动换行。现在这些操作统一使用 adaptive `LazyVGrid`：按钮共用 32 点高度、10 点间距和最小宽度，宽度不足时自动减少列数。

真实写入库存系统是唯一的强调按钮；查询、模拟和材料整理使用次要样式。页头只保留资料状态，更新与刷新移入可换行的操作区，避免固定高度页头在窄窗口中争抢水平空间。UI 回归测试同时锁定按钮最小宽度、间距，并验证常规宽度可并排、窄宽度会退化为单列。
